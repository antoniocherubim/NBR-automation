# CI-001 — Validação privada e artifact do repositório

## Objetivo

Criar uma workflow do GitHub Actions que valide o snapshot rastreado e, somente após todos os gates passarem, disponibilize um arquivo único chamado `artifact.zip` contendo o repositório daquele commit.

O artifact é privado, inclui os arquivos rastreados em `inputs/`, não contém `.git/` e expira inicialmente após sete dias.

## Contexto

REPO-001, REPO-002 e DOCS-001 estão integradas. Os gates locais verificam ambiente, hashes, testes, documentação e whitespace, mas ainda não existe validação automática no GitHub nem pacote para download.

O repositório é privado e, no estado operacional informado, somente o proprietário possui acesso. Mesmo assim, `artifact.zip` deve ser tratado como sensível porque contém norma, template e plantas rastreadas. Pessoas autenticadas com acesso de leitura ao repositório podem baixar artifacts enquanto eles existirem.

O harness é ferramenta externa de desenvolvimento e será removido em uma etapa final do projeto. CI-001 não acopla a workflow ao modo de aprovação do harness e não testa valores como `none`, `telegram` ou `github_pr`.

O run local desta task permanece offline. A workflow versionada somente será executada pela infraestrutura do GitHub depois de integrada e enviada pelo operador.

Comando esperado:

```bash
../codex-cursor-agent-loop/agent-loop run \
  --repo "$PWD" \
  --require-profile \
  docs/tasks/CI-001.md 5 "$BASE_SHA"
```

## Escopo permitido

### 1. Workflow

Criar uma única workflow, preferencialmente em:

```text
.github/workflows/validate-and-package.yml
```

Triggers permitidos nesta versão:

- `push` para `main`;
- `workflow_dispatch` manual.

Não usar `pull_request`, `pull_request_target`, cron, release ou chamada por workflow externo nesta task.

Configuração mínima:

- runner `ubuntu-24.04`;
- timeout explícito e conservador;
- `permissions: contents: read` no menor escopo possível;
- concurrency por workflow/ref, com cancelamento de execução anterior da mesma ref;
- shell Bash com comportamento fail-fast;
- nenhum environment protegido, secret ou token personalizado;
- checkout sem persistir credenciais e com histórico mínimo suficiente.

### 2. Actions externas pinadas

Toda action externa deve usar SHA completo e comentário com a versão verificada. Para o baseline pesquisado em 2026-08-20:

```yaml
uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6.0.2
uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
```

Não usar tag flutuante (`@main`, `@v6`, `@v7`) nem action de terceiro adicional. Atualização futura de SHA exige task/review dedicado.

### 3. Gates da CI

Executar, antes de criar o ZIP:

```bash
sha256sum -c SHA256SUMS
bash scripts/agent-loop/bootstrap.sh
bash scripts/agent-loop/test.sh
git diff --check
```

Também confirmar:

- Python disponível satisfaz 3.12+;
- os 14 inputs retornam sucesso;
- suíte completa termina sem failure/error/skip inesperado;
- checkout rastreado permanece limpo após os gates;
- nenhum output temporário é criado sob `inputs/`;
- nenhum artifact é enviado quando qualquer passo anterior falha.

Não instalar pacotes, executar `pip`, `apt`, `curl`, `wget` ou acesso Git remoto adicional. O runner já deve fornecer as ferramentas mínimas; ausência falha de forma explícita.

### 4. Construção de `artifact.zip`

Depois dos gates, criar o pacote a partir do objeto Git do commit, não por `zip -r` do workspace:

```bash
git archive --format=zip --output=artifact.zip "$GITHUB_SHA"
```

O pacote deve:

- representar exatamente os arquivos rastreados no commit validado;
- incluir `inputs/`, `SHA256SUMS`, código, documentação, schemas, manifests e workflow;
- incluir temporariamente `.agent-loop/` enquanto fizer parte do repositório de desenvolvimento;
- excluir naturalmente `.git/`, ignored files, caches, logs, outputs e credenciais;
- não incluir o próprio `artifact.zip`;
- preservar nomes Unicode;
- ser validado estruturalmente antes do upload;
- ter SHA-256 calculado e exibido no log/resumo da job.

Usar Python stdlib (`zipfile`) e Git para confrontar as entradas do ZIP com os paths de blobs do commit. Rejeitar path absoluto, `..`, duplicidade, CRC inválido, entrada inesperada ou ausência de arquivo rastreado.

### 5. Upload

Enviar somente o arquivo `artifact.zip` com upload direto suportado por `actions/upload-artifact@v7.0.1`:

```yaml
with:
  path: artifact.zip
  archive: false
  if-no-files-found: error
  retention-days: 7
```

Como `archive: false` aceita somente um arquivo e usa o nome desse arquivo, não criar ZIP externo contendo outro ZIP. O download esperado deve ser o próprio `artifact.zip`.

Registrar no summary da job, sem expor secrets:

- commit completo;
- resultado dos gates;
- tamanho do ZIP;
- SHA-256 local;
- artifact ID/URL/digest fornecidos pela action quando disponíveis;
- aviso de conteúdo privado e retenção de sete dias.

### 6. Documentação

Atualizar materialmente:

- `README.md`;
- `ROADMAP.md`;
- `docs/GETTING_STARTED.md`;
- `docs/PRIVACY.md`;
- este registro de task.

Durante o candidate, descrever CI-001 como candidate/aguardando integração. Não declarar workflow disponível antes de integração e push do operador.

Documentar como localizar e baixar o artifact pela interface GitHub e, opcionalmente, com GitHub CLI já autenticada, sem inserir owner, URL privada ou token hardcoded.
